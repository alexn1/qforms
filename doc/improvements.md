## Топ-10 рекомендаций (по приоритету)

### 1. Убрать `eval` с данными из запроса (безопасность, срочно)

`BkField.fillDefaultValue` (`src/backend/viewer/BkModel/BkField/BkField.ts:45`) подставляет параметры в JS-строку через `Helper.templateToJsString` и выполняет её через `eval`. Значение вклеивается как `'${JSON.stringify(v)}'`. `JSON.stringify` не экранирует одинарную кавычку, а среди параметров есть cookies и параметры запроса (`Context.getAllParams`). Если `defaultValue` ссылается на такой параметр, это похоже на выполнение произвольного кода на сервере. Эксплуатация не проверялась.

Тот же приём используется в:
- `src/backend/viewer/BkModel/BkParam/BkParam.ts:18`
- `src/backend/viewer/BkModel/BkDatabase/BkNoSqlDatabase/BkMongoDbDatabase/BkMongoDbDatabase.ts:91`
- `src/frontend/viewer/Model/Field/Field.ts:34`, `:80`

Что сделать: как минимум передавать значения как аргументы функции, а не вклеивать их в исходный код. Лучше — заменить на безопасный вычислитель выражений.

### 2. Остальная безопасность

- `BkPostgreSqlDatabase.ts:214` — запрос собирается конкатенацией (`table_name = '${table}'`). Нужно использовать параметры.
- `BkApplication.ts:328` — пароль приложения хранится открытым текстом в JSON и сравнивается через `===`. Нужны хеширование (bcrypt/argon2) и сравнение за постоянное время.
- Обновить зависимости с critical и high уязвимостями (`npm audit`).

### 3. Довести TypeScript до нуля ошибок

Сборка идёт через esbuild/ts-loader без проверки типов, поэтому ошибки копятся незаметно.

1. Добавить скрипт `"typecheck": "tsc --noEmit"`.
2. Починить существующие ошибки, начиная с `src/backend`.
3. Постепенно убрать `@ts-ignore` и `any`.

### 4. Включить линтер и форматирование в процесс

- Добавить скрипт `lint`.
- Прогнать `eslint --fix` и `prettier --write` отдельным коммитом.
- Сделать ошибки ESLint блокирующими.
- Добавить pre-commit hook (husky + lint-staged).

### 5. Тесты

- Unit-тесты на генерацию SQL (insert, update, delete) для Postgres и MySQL.
- Тесты загрузки JSON-моделей.
- E2E-тесты CRUD для каждой поддерживаемой БД.
- Перевести e2e-тесты с импорта из `dist` на `src`, чтобы перед прогоном не требовалась сборка.

### 6. CI (GitHub Actions)

Typecheck, lint и тесты с Postgres в виде service-контейнера. Без CI пункты 3–5 со временем откатятся назад.

### 7. Убрать сгенерированное и мёртвое из git

- Добавить `dist/` в `.gitignore` и собирать пакет в `prepublishOnly`.
- Удалить `old/` (останется в истории git).
- Удалить закомментированный код (например, второй `decodeValue` в `src/frontend/common/Helper.ts`).

### 8. Обновить устаревшие зависимости

- `ws@2` → 8
- `glob@5` → `fast-glob` или `fs.glob`
- `mysql` → `mysql2` (поддерживает промисы и активно развивается)
- React 17 → 18
- `chai@3` и `should` выглядят неиспользуемыми рядом с jest
- Node 16 (`.nvmrc`) давно вышел из поддержки, стоит перейти на 20 или 22

### 9. Схема и валидация JSON-моделей

Атрибуты хранятся строками (`"authentication": "false"`, `"startup": "true"`) и читаются через нетипизированный `getAttr`. Стоит описать JSON Schema или zod-схему для каждого `@class`, валидировать при загрузке и получить типизированные атрибуты. Это уберёт целый класс ошибок и поможет редактору.

### 10. Разбить крупные классы и упростить сборку

- `BackHostApp.ts` (724 строки) отвечает за пути, сервер, websocket, модули и процесс. Разделить на конфиг, сервер и реестр приложений.
- `BkApplication.ts` (638 строк) и `frontend/viewer/Model/DataSource/DataSource.ts` (607 строк) — аналогично.
- Сборку (шесть webpack-конфигов плюс gulp) можно заменить на Vite или один esbuild-скрипт.

## Порядок работы

1. Пункты 1–2 (безопасность), примерно день-два.
2. Пункты 6, 3, 4: сначала CI с проверкой типов и линтером в режиме «только новые ошибки», потом постепенная чистка.
3. Пункт 5 (тесты) — параллельно с остальными изменениями.
